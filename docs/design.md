# 설계 — upload-fit

승인 2026-10-22. 결정이 바뀌면 코드보다 이 파일을 먼저 고친다.

## 문제
업로드 규격(px·용량·형식)이 사이트마다 다르고, 기존 도구는 규격을 사람이 직접 고르거나 입력해야 한다.
비슷한 확장(Remage, UploadReady)도 규격을 수동으로 입력하는 방식이라 사용자가 3~4명이다.
**차별점: 업로드 칸 근처 안내문을 읽어서 자동으로 맞춘다.**

## 결정
| 항목 | 결정 | 포기한 대안 |
|---|---|---|
| 규격 감지 | 업로드 칸 주변 텍스트를 정규식으로 파싱하고, 확인 카드로 사용자 승인을 받음 | LLM 추출 (API 키·비용·페이지 내용 외부 전송), 사이트별 프리셋만 사용 (Remage와 같아짐) |
| 안내문 없는 사이트 | hostname 기준 프리셋을 보조로 사용. 필요한지는 0단계 결과를 보고 확정 | — |
| 파일 바꿔치기 | `window` capture 단계 `change` → `stopImmediatePropagation` → 변환 → `DataTransfer`로 `input.files` 교체 → `change` 다시 디스패치 | input 엘리먼트 교체 (React/Angular ref가 깨짐) |
| 스택 | MV3, 바닐라 JS, 빌드 도구·의존성 없음 | WXT (파일이 10개를 넘거나 popup이 생기면 이전) |
| 규격 객체 형태 | `{ sizes, minSize, maxSize, minSide, maxSide, ratios, maxBytes, formats }` — `sizes`: 정확한·권장 크기 목록 (ASC는 기기당 여러 개), `minSize`/`maxSize`: 가로·세로 각각의 하한·상한 ("300 X 400 픽셀 이상"), `minSide`/`maxSide`: 방향 무관 변 범위 (Play). 문구에 나온 키만 채운다. 없거나 모호하면 `null` | — |
| 규격으로 인정하는 줄 | 요구 표현(이하·최대·~해 주세요·must…)이 있는 줄만. 줄끼리 같은 키에 다른 값을 말하면 `null` | 모든 줄 (Play 애셋 패널의 "크기: 1080x1920px" 메타데이터를 규격으로 오인) |
| 크기 뒤 수식어 | 사이 → 변 범위, 이상 → `minSize`, 이내·이하·미만 → `maxSize`, 없음·권장·기준 → `sizes`. "사이즈"의 사이는 제외 | — |
| 용량 단위 | KB·MB는 1000 단위 | 1024 단위 (사이트가 1000 단위로 검사하면 한도를 넘어 거부됨) |
| 모호한 `A X B` | 같은 문구의 비율과 모순되거나 "사이"가 붙으면 크기가 아니라 변 범위 (`minSide`/`maxSide`) | — |
| 규격 찾는 기준점 | input이 아니라 **사용자가 마지막으로 클릭한 업로드 트리거** 주변 | input 주변 (Play Console은 input이 공용 패널 안에 있어서 실패) |

## 단계
- [x] **0. 샘플 수집** — 대상 사이트의 업로드 칸 주변 원문을 `spec.test.js` 케이스로 옮긴다 (기대 규격 포함, 이 시점엔 실패가 정상).
  완료: 8곳 이상 케이스 수록, Play Console·ASC에 규격 문구가 있는지 확정해서 아래 "확인된 사실"에 기록
- [x] **1. `spec.js` 파서** — 텍스트 → 규격 객체.
  완료: `node --test` 통과
- [ ] **2. 가로채기 패스스루** — `change`를 잡아서 같은 파일을 다시 넣기만 한다.
  완료: Play Console·ASC·로컬 테스트 페이지에서 업로드가 평소와 같고, 페이지 `change` 핸들러가 1회만 호출됨
  진행: 로컬 테스트 통과 (`./test-browser.sh`). 실제 사이트 확인은 확장을 Chrome에 로드한 뒤 (사용자)
- [x] **3. 규격 위치 찾기** — 기준점 후보 = 최근 클릭들(새 것부터, capture 단계 `click` 기록) → input의 `aria-describedby` → input 자신. 후보마다 조상으로 올라가며 `parseSpec(innerText)`가 처음 null이 아닌 곳을 채택. 패널 안 "업로드" 버튼에서 출발하면 패널엔 요구 표현이 없고, 더 올라가면 슬롯 규격이 섞여 모호(null)하므로 자연히 그 전 클릭("애셋 추가")으로 넘어간다. 꼭대기까지 가도 규격이 하나뿐이면 그게 페이지 유일 규격 폴백이다.
  완료: 로컬 테스트 페이지(공용 패널 구조 재현 포함)에서 슬롯별로 올바른 규격이 찍히고, 규격 없는 페이지는 `null`
- [x] **4. `convert.js`** — 리사이즈, cover/contain, 포맷 변환, 품질 이진탐색으로 용량 맞춤, 알파 평탄화, EXIF 회전, 다중 파일.
  완료: `test.html`에서 결과물의 px·bytes·type이 규격과 일치
- [ ] **5. 확인 카드** (Shadow DOM) — "감지: 1320×2868 PNG ≤8MB · [자르기/여백] · [적용] [원본]".
  완료: Play Console에 1080×2340 캡처 → 적용 → 규격 에러 없이 업로드
  진행: 로컬 전체 흐름 테스트 통과 (적용·여백·원본·Esc·이미 맞음·HEIC). 실제 업로드는 Play 애셋 라이브러리에 파일이 추가되므로 사용자가 직접
- [ ] **6. 프리셋 폴백** (0단계에서 필요하다고 확정될 때만).
  완료: ASC 6.9" 슬롯에 1170×2532 → 1320×2868로 변환되어 수락

## MVP에서 빼는 것
드래그앤드롭 업로드 (`drop`의 `dataTransfer.files`는 읽기 전용), HEIC (Chrome이 디코딩 못 함), LLM 파서, 설정 팝업, 웹스토어 배포

## 리스크 — 아직 가정
- ASC 업로드 칸에는 규격 문구가 없고, 틀리면 업로드 후 "The dimensions of one or more screenshots are wrong." 에러만 뜰 것 — 공개 자료로 추정 (화면 이미지는 못 찾음). 팀원 계정으로 확인 필요. 맞다면 6단계 프리셋이 필요하다
- 프레임워크가 합성 `change` 이벤트를 받을 것 → 2단계에서 확인 (Play Console은 Angular)
- canvas의 PNG 출력은 항상 RGBA라서 알파 채널을 거부하는 곳(Apple, Play 그래픽)에 걸릴 수 있음 → 4단계 결정: JPEG가 허용되면 JPEG, 원본에 투명 영역이 있고 PNG가 허용될 때만 PNG. 실제 업로드로 수락되는지는 미확인
- `browser.test.js`는 macOS Chrome 경로를 기본값으로 쓴다 (`CHROME` 환경변수로 변경). 없으면 건너뜀
- cm 규격은 DPI를 가정해야 함 → 비율로만 쓰고, px는 사이트가 명시할 때만 신뢰
- shadow DOM 안의 input은 못 잡음 — `change`는 `composed: false`라서 shadow root 밖(window)까지 안 나온다 (open이어도 마찬가지)
- 우리가 다시 쏘는 이벤트는 `isTrusted: false` — 이걸 검사하는 사이트는 동작 안 함 (아직 본 적 없음)
- 카드 이벤트는 host에서 전파를 막지만, 페이지가 capture 단계에서 듣는 "바깥 클릭/Esc" 리스너(Radix·Headless UI 일부)는 못 막는다. 그 경우 모달이 닫혀 input이 사라지면 "업로드 칸이 닫혀서…" 토스트로 알린다
- 페이지가 file input에 `input` 이벤트만 직접 쏘면(뒤따르는 `change` 없이) 우리가 삼킨다 — `isTrusted` 검사로 고칠 수 있지만 test.html의 합성 선택이 깨진다 (CDP `DOM.setFileInputFiles`로 바꿔야 함)
- 한 번에 고른 `a.png`와 `a.jpeg`가 둘 다 `a.jpg`가 된다 (이름 충돌)
- `findSpec`은 텍스트가 1만 자를 넘는 조상에서 멈춘다 → 약관이 긴 페이지에선 "페이지에 규격이 하나뿐이면 그걸 쓴다" 폴백도 꺼진다 (오탐을 줄이려는 의도된 절충)

## 확인된 사실
단계를 진행하면서 위 "가정"을 확인되는 대로 여기로 옮긴다.

**Play Console 기본 스토어 등록정보 (2026-10-22, 실제 화면)**
- 규격 문구는 슬롯마다 본문에 있다 (아이콘·그래픽 이미지·휴대전화·7/10인치 태블릿·데스크톱·XR). 원문은 `spec.test.js`.
- 페이지 처음엔 `input[type=file]`이 없다. "애셋 추가" → 오른쪽 **애셋 라이브러리 패널**이 열리고, 그 하단 `simple-uploader` 안에 input 하나가 생긴다. 모든 슬롯이 이 input 하나를 공유한다.
- 패널의 "업로드" 버튼은 그 input에 `click()`을 호출한다. input은 DOM에 연결돼 있고 shadow DOM이 아니다 (`multiple`, `accept=".jpeg,.jpg,.png"`, `display:none`). → `window` capture `change` 방식은 유효.
- 규격 문구(본문)와 input(패널)이 DOM상 멀다 → 3단계 기준점을 "마지막 클릭"으로 바꾼 이유.
- 패널에 "자르기 필요" 필터가 있다 — Play 자체 크롭 기능이 있는지는 미확인.
- 슬롯 장수 규칙("2~8장")은 범위 밖. 파서는 무시한다.
- 3단계 실제 검증 (spec.js + findSpec을 페이지에 주입, 파일 선택창은 막고): 휴대전화 "애셋 추가" → "업로드" → `{minSide:320, maxSide:3840, ratios:16:9/9:16, 8MB, jpeg/png}`, 앱 아이콘 → `{sizes:[[512,512]], 1MB}`. "업로드"에서 출발한 탐색은 null로 건너뛰어짐.
- 공용 input의 `multiple`은 슬롯마다 바뀐다 (아이콘 슬롯에선 false).
- 애셋 패널은 애셋마다 "가로세로 비율: 9∶16"(U+2236), "크기: 1080x1920px" 메타데이터를 보여준다 → "요구 표현이 있는 줄만" 규칙의 이유. 페이지 전체 텍스트는 1,838자(패널 열면 6,282자)라 길이 제한으로는 못 막는다.

**공개 안내 페이지 (2026-10-22, curl 원본)**
- 한국 원서·증명사진 사이트의 업로드 화면은 전부 로그인이 필요하다 → 같은 사이트의 공개 안내문을 테스트에 쓴다 (19건, `spec.test.js`).
- Play에 없던 표현: "가로 ○, 세로 ○", "이상"(최소)·"이내"(최대), "395~431" 범위, 단위 없는 "(3X4)", "㎝", "pixel", "350KB 미만". Q-Net은 같은 크기를 한 FAQ에선 "이상", 다른 FAQ에선 "이내"라고 쓴다.
- Apple 도움말의 크기 목록은 표 형태("1320 x 2868 pixels" 다음 줄 "(portrait)")라 요구 표현이 없다 → 파서 대상이 아니고 6단계 프리셋의 원천이다.
- 고용24·워크넷: 공개된 사진 규격 문구를 찾지 못했다.
